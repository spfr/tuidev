# Security Policy

## Supported versions

| Version | Supported |
|---------|-----------|
| 3.x (latest minor on `main`) | :white_check_mark: |
| 2.x and earlier | :x: |

## Reporting a vulnerability

Please do **not** open a public issue. Use GitHub's private vulnerability reporting (Security → Report a vulnerability) or email the maintainers. Include the affected file or command, your tuidev version (`tuidev version`), your OS, and reproduction steps. Give us a reasonable window to fix the issue before you disclose it.

Especially in scope: a Seatbelt profile (`configs/sandbox/profiles/*.sb`) or `bin/sbx` that lets a sandboxed process read a denied credential path or write outside the project directory; an installer or uninstaller step that destroys user data outside what the manifest records; and shipped agent settings that weaken the documented boundary.

## Security model

- **Sandboxed agents.** `--pack ai-clis` ships Claude Code and Codex with their native sandboxes on, so plain `claude` and `codex` run confined. Codex's `workspace-write` limits writes and network but not reads; for credential-sensitive Codex work use `sbx -- codex -s danger-full-access -a on-request`. `sbx` (macOS Seatbelt) confines any other command. Under `sbx` (and, for Claude Code's Bash tool and `Read`, under its native sandbox and shipped deny rules), credential stores such as `~/.ssh`, `~/.aws`, `~/.gnupg`, the Keychain, `~/.config/gh`, cloud CLIs, package-registry tokens and password stores are denied for both reads and writes. The full list, and what Seatbelt cannot do (per-host network rules), is in [docs/sandboxing.md](docs/sandboxing.md).
- **Secrets stay out of the repo and out of your shell.** `secret` keeps tokens in the macOS Keychain, libsecret or `pass` and hands them to one command at a time (`secret run -n NAME -- CMD`). It is one person's tokens on one machine, not a team or deployment secret manager, and it is not a sandbox: the command you give a token has it, and Codex under `workspace-write` can read the stores. What it does and does not protect is in [docs/secrets.md](docs/secrets.md). Nothing is written to the repo: `~/.zshrc.local` is yours and is gitignored in a clone; tuidev writes to it once at most, when a migration moves your own toolchain lines out of its block into a marked section there, and never puts a token in it. Set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` to keep them out of the environment that agent subprocesses inherit.
- **The link watcher trusts your own machines, and only for a few things.** `agents link watch` keeps an outbound ssh to each of your other machines and reads requests from it; nothing listens. Any process on such a machine can send a request, so a machine you follow may make this one open a tab on `127.0.0.1` for a `localhost` URL (through a tunnel the watcher picks the port for, at most eight a machine) or fetch and open a file with a viewer's extension (at most 50 MB), five requests a machine in ten seconds. It cannot run anything, and it can ask for one of your files only through a dialog you must answer, one file at a time. Don't follow a machine you would not open a dev server from; `AGENTS_LINK=0` turns the watcher off. The full rules are in [docs/remote.md](docs/remote.md#remote-feels-local-ports-links-and-files).
- **No third-party installer is piped into a shell for you.** When a package manager can't provide a tool, the installer prints the vendor's official install command for you to review and run. Read any `curl … | sh` command before you run it yourself.
- **tuidev's own one-line install is one short script.** [`get.sh`](get.sh) downloads the release archive, refuses it unless its sha256 matches the one the release lists, every path stays inside one directory and it holds no symlink or hard link, and asks on your terminal before it runs the installer (with no terminal, it installs only with `--yes`). The checksum catches a truncated or mismatched download, not a hostile release: `get.sh` itself trusts HTTPS to github.com and whoever can publish a tuidev release. The archive is built with `git archive` from the tagged commit, so it holds committed files only. To read before running, download `get.sh` and run `bash get.sh`, or clone the repo. `tuidev update` uses the same script for later releases, and nothing updates without you asking.
- **Each release has a signed provenance you can check.** A pushed tag is released by [`release.yml`](.github/workflows/release.yml) only after all of CI passes on that commit; it builds the three assets on GitHub's runners and signs a build provenance for each (GitHub artifact attestations, through Sigstore), which names the workflow and the commit. With `gh` logged in, `gh attestation verify tuidev.tar.gz --repo spfr/tuidev --signer-workflow spfr/tuidev/.github/workflows/release.yml` checks a download; run it on `get.sh` before `bash get.sh` to check the installer too. `get.sh` does not run it for you, since that would need `gh` and a login on every machine it installs. Releases before 3.23.0 have no assets and no provenance.
- **The update check sends nothing about you.** Once a day `tuidev` asks github.com where `releases/latest` redirects to: one request, no body and no identifier beyond the request itself (your IP address, curl's user agent). `tuidev latest off` turns it off.
- **Non-destructive by default.** `--dry-run` previews every mutation, overwritten files are backed up to `~/.config/tuidev/backups/`, and `tuidev uninstall` removes only what the install manifest records.
- **Pinned CI.** GitHub Actions are pinned to commit SHAs and updated by Dependabot.

Keep tools current with `tuidev update --packages`, and audit Tailscale, SSH permissions and Seatbelt profile drift with `tuidev update --security`.
